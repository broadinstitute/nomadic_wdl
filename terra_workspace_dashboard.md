# Workspace title: Malaria\_Plasmodium\_ONT\_Amplicon\_Nomadic

**Welcome to the Nomadic workspace!**

![Screenshot: Workspace title: Malaria_Plasmodium_ONT_Amplicon_Nomadic](https://raw.githubusercontent.com/broadinstitute/nomadic_wdl/main/imgs/overview_01_workspace-title-malaria-plasmodium.png)

This workspace hosts the Nomadic and NomadicSummary workflows. Nomadic is designed for rapid processing and analysis of *Plasmodium* amplicon sequencing data, while NomadicSummary evaluates quality control and mutation prevalence across a set of experiments. Amplicon sequencing is a targeted DNA sequencing technique that selectively amplifies and sequences specific regions of interest within a genome. Nomadic utilizes specific sequencing panels that target key genetic markers across the *P. falciparum* genome, including loci associated with antimalarial drug resistance, rapid diagnostic test evasion, and vaccine targets like *csp*.

Originally built to facilitate rapid genomic surveillance in resource-limited settings, the Nomadic and NomadicSummary workflows offer a specialized bioinformatics pipeline specifically for Oxford Nanopore (ONT) sequencing data. While Nomadic processes raw ONT FASTQ files to produce quality control and coverage summary tables (CSVs), filtered variant calls (VCFs), and drug-resistance markers, NomadicSummary evaluates quality control and mutation prevalence across a broader set of experiments.

These versions of the pipelines available in Terra serve as a complementary instantiation to the original real-time pipelines. By making both Nomadic and NomadicSummary available in Terra, users can analyze data and aggregate multi-experiment summaries in the cloud when a high-powered laptop is not available locally. This cloud-based environment also enables users to share and collaborate across different sites, organize and manage data by linking genomic outputs to metadata, and scale analysis to larger sets of samples than may be possible on a single local machine.

## Overview of workflows:

This workspace currently contains two workflows; Nomadic and NomadicSummary.

**Nomadic**

**Goal:** Transform raw sequencing data into clean, mapped genomic variants.

This workflow handles the primary bioinformatic heavy lifting for the pipeline. To begin, the user provides a set of raw ONT FASTQ files and sample identifiers. The process performs read mapping with minimap2, sample quality control and amplicon coverage evaluation with samtools, and variant calling with delve or bcftools.

Reads are aligned to a reference genome (typically *P. falciparum* 3D7) to identify genetic variations—such as single nucleotide polymorphisms (SNPs)—resulting in standard VCF files and tables of drug-resistance markers. Additionally, the workflow generates quality control and coverage summary files to help users evaluate dataset quality.

**NomadicSummary**

**Goal:** Aggregate and summarize quality control metrics and mutation prevalence across multiple runs or experiments.

NomadicSummary compiles outputs generated by the Nomadic workflow across multiple distinct experiments or batches. It evaluates sample and amplicon quality control criteria, tracks regional coverage, and computes overall prevalence for key drug-resistance and genetic diversity markers, generating consolidated summaries and reports for multi-experiment analysis.

**ONTBasecallDorado (Optional)**

**Goal:** Convert raw Nanopore signal files (POD5) into basecalled, demultiplexed reads.

Nanopore sequencers do not output DNA sequences directly. They record the electrical current as each strand passes through a pore, and a separate step, called basecalling, translates that signal into A, C, G and T. MinKNOW normally does this on the sequencing computer, but on a laptop without a strong GPU it is slow and it is sometimes switched off during a run or re-done afterwards with a more accurate model.

This workflow performs basecalling in the cloud on a GPU machine using Oxford Nanopore's Dorado basecaller. You point it at the folder of POD5 files from a run and tell it which basecalling model and barcoding kit were used; it returns one set of reads per barcode together with sequencing summary files. If your run was already basecalled in MinKNOW with the model you want, you can skip this workflow and start with Nomadic.

## ONTBasecallDorado

### Running ONT Basecalling (Dorado) via Terra

The ONTBasecallDorado workflow is an optional first step that is only needed when a run has not been basecalled, or when you want to re-basecall it. Typical cases are: basecalling was switched off in MinKNOW so the experiment folder contains POD5 files but no `fastq_pass` folder; the run was basecalled with the *fast* model to keep up with the sequencer and you want the more accurate *sup* model before variant calling; or the wrong barcoding kit was selected in MinKNOW and the run needs to be demultiplexed again. If MinKNOW already produced `fastq_pass` folders with the model you want, skip this tab and go straight to Running Nomadic Pipeline via Terra.

The workflow is the Broad Institute's ONTBasecallDorado pipeline (repository `broadinstitute/long-read-pipelines`, version 4.0.69), configured in this workspace for *P. falciparum*. If you cloned the Template workspace it is already listed under Workflows. If you are starting from a different workspace, the workflow is located here in Dockstore `[link: dockstore.org/workflows/github.com/broadinstitute/long-read-pipelines/ONTBasecallDorado]` and can be imported by selecting "Terra" under "Launch with".

What the workflow does, in order:

1. Lists every `.pod5` (and `.fast5`) file in the folder you provide, including sub-folders.
2. Splits the files into batches of about 100 so that several GPU machines basecall in parallel.
3. Runs `dorado basecaller` on each batch (one NVIDIA V100 GPU per batch) with the model you choose. Because the Pf3D7 reference genome is supplied, Dorado also aligns the reads while basecalling, so the output is an aligned BAM rather than a plain FASTQ.
4. Runs `dorado demux` to split reads by barcode (plus an `unclassified` file for reads whose barcode could not be read). If no barcode kit is given, reads are kept together.
5. Merges the per-batch sequencing summaries into one `sequencing_summary.txt` and writes a MinKNOW-style `final_summary.txt`.
6. Copies everything to a time-stamped folder in the workspace bucket and records the location in your data table.

Software: Dorado 1.4.0 (`us.gcr.io/broad-dsp-lrma/lr-dorado:1.4.0`). Reference: *P. falciparum* 3D7, PlasmoDB release 61.

### Setting up workflow

#### Defaults and Expectations

Unlike the Nomadic workflow, this workflow does not guess paths from the experiment name: you must give it the explicit `gs://` path to the folder containing the raw POD5 files. Everything else is either optional or already set in the workflow configuration (reference genome, output location).

##### Expected File Locations

If you upload the whole MinKNOW experiment folder as described in the Nomadic tab (`gs://{bucket}/minknow/{experiment_name}`), the POD5 files are already in the bucket and you can point the workflow at them directly:

- POD5 folder: `gs://{bucket}/minknow/{experiment_name}/.../pod5_pass` (or `pod5`, depending on your MinKNOW version)

The workflow searches sub-folders, so you may also point it at the experiment folder itself. NOTE: if you do, any `pod5_fail` and `pod5_skip` folders will be basecalled too. Point at `pod5_pass` (or `pod5`) if you want only the reads MinKNOW kept.

Outputs are written to `{gcs_out_root_dir}/{experiment_name}/{timestamp}/`, where `gcs_out_root_dir` is fixed in the workflow configuration `[fill in the configured path, currently …/results/test]`. Each launch creates a new time-stamped folder, so re-running never overwrites earlier results.

##### Basecalling models

The `config` input tells Dorado which basecalling model to use. The simplest values are an accuracy level, and Dorado picks the right model for your flow cell chemistry from the POD5 files:

| Value | Meaning | When to use |
| --- | --- | --- |
| `fast` | Fastest, least accurate | Quick checks only |
| `hac` | High accuracy | Reasonable compromise when turnaround matters |
| `sup` | Super accuracy (slowest, several times the GPU time of `hac`) | Recommended for variant calling and drug-resistance markers |

You can pin a model version (e.g. `sup@v5.0.0`) or give a full model name (e.g. `dna_r10.4.1_e8.2_400bps_sup@v5.0.0`) if you need results to be reproducible across runs. The model must exist in Dorado 1.4.0.

#### Uploading Data to the Workspace Bucket `[Heading5]`

Raw POD5 data are uploaded in the same way as MinKNOW outputs in the Nomadic tab (Dashboard → Storage Details → "Open bucket in browser" → Upload → Upload folder). Two notes specific to raw data:

- POD5 folders are large (tens to hundreds of GB for a MinION run). Browser uploads of this size are slow and can fail; the `gsutil` command-line tool is more reliable: `gsutil -m cp -r pod5_pass gs://{bucket}/minknow/{experiment_name}/`.
- Dorado 1.4 works with POD5. If you have an older run that only produced FAST5 files, convert them first with ONT's `pod5` tool (`pod5 convert fast5`) before uploading. `[verify: whether the lr-dorado:1.4.0 container still accepts FAST5]`

| 2026\_01\_14\_new\_dbs | gs://{bucket}/minknow/2026\_01\_14\_new\_dbs/…/pod5\_pass | sup | SQK-NBD114-96 | MinION | FAX12345 |

A few notes about wiring these inputs:

- In the workflow inputs configuration, all strings are required to be wrapped in quotes (i.e. `"sup"`, not `sup`) unless they are `this.{column}` references.
- `barcode_kit` must be the kit used at library preparation, not the sequencing kit. If almost all reads end up in `unclassified`, this is the first thing to check.
- The reference inputs are optional in the workflow itself. If you clear them, the output BAMs will be unaligned.
- The workflow is written for *P. falciparum* here. For *An. gambiae* runs you would need to change the three reference inputs to the AgPEST reference.

### Outputs of Basecalling

After the run completes, two columns are filled in on the experiment table:

- `basecalled_output_dir` — the `gs://` folder containing all outputs for the run.
- `barcodes` — the list of barcode files that were produced.

The output folder is organised as follows:

```
{gcs_out_root_dir}/{experiment_name}/{timestamp}/
    SQK-NBD114-96_barcode01/
        pass/                                   aligned BAM file(s) for this barcode
        sequencing_summary.SQK-NBD114-96_barcode01.txt
        final_summary.SQK-NBD114-96_barcode01.txt
    SQK-NBD114-96_barcode02/
        ...
    unclassified/
        ...
```

Each barcode folder holds the reads for that barcode as BAM files that are already aligned to Pf3D7 (one BAM per basecalling batch, so there may be several files in `pass/`), a per-barcode sequencing summary with one line per read (read ID, length, mean quality, barcode), and a `final_summary.txt` with the run metadata (instrument, flow cell ID, sample ID, run ID, start and stop times, basecalling model). NOTE: the workflow does not apply a pass/fail quality filter of its own; all basecalled reads are placed under `pass/`. `[verify: Dorado 1.4 default --min-qscore behaviour]`

### Troubleshooting

| What you see | Likely cause | What to do |
| --- | --- | --- |
| Workflow finishes in minutes with no `Basecall` tasks, or `Basecall` fails with no input files | `fast5_dir` points to a file, has a typo, or the folder has no `.pod5` files | Check the path with "Open bucket in browser" or `gsutil ls`; it must be the folder holding the POD5 files (or a parent of it). |
| `Basecall` fails with a model download / "model not found" error | `config` is not a model Dorado 1.4 knows | Use `fast`, `hac` or `sup`, or check the full model name against Dorado's model list. |
| Nearly all reads are in `unclassified` | Wrong or mis-typed `barcode_kit` | Confirm the kit used at library prep; the code must match ONT's naming exactly. |
| `Basecall` tasks fail once and restart, or the submission fails after a retry | Preemptible GPU machines were reclaimed | Relaunch with call caching on; finished batches are reused. |
| `Basecall` tasks stay queued for a long time | GPU quota in the billing project (us-central1) is used up | Check the quota in the Google Cloud console, or wait for other submissions to finish. |
| Permission denied in the first task | The POD5 folder is in a bucket this workspace cannot read | Upload into the workspace bucket, or grant the workspace proxy group *Storage Object Viewer* on the other bucket. |
